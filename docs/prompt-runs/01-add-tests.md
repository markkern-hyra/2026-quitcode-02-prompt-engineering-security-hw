# Прогін 01 — `add-tests`: v1 → meta-prompting → v2 (markdown vs XML)

Промпт: [`prompts/add-tests.md`](../../prompts/add-tests.md). Методика — [README](./README.md).

## 01a — meta-prompting над v1

Запит: «Покращ цей промпт перед виконанням і поясни, які acceptance criteria ти
б додав. Сам промпт не виконуй…» + текст v1.

| | |
|---|---|
| Ходів / вартість / час | 4 / $0.23 / 71 с |
| Що прочитав | `app/src/quote.ts`, `app/src/quote.test.ts`, `app/package.json` |
| Змінені файли | жодного |

Агент запропонував 9 доповнень і сам підсумував: «Оригінальний промпт був уже
непоганим — покращення здебільшого стосуються **конкретизації**».

| Пропозиція | Рішення | Чому |
|---|---|---|
| Наявні тести не видаляти й не змінювати | ✅ прийнято | LLM іноді «оптимізує» чужі тести |
| Заборона `.only` / `.skip` / `console.log` | ✅ прийнято | типові залишки дебагу |
| Інваріант `Number.isInteger` для сум у центах | ✅ прийнято | фіксує очікування домену |
| `it.fails` має перевіряти **правильну** поведінку | ✅ прийнято | інакше `it.fails` можна «виконати» будь-яким тестом, що падає |
| Явний перелік невизначених випадків | ✅ прийнято (як «напр.») | структурує «Відкриті питання» |
| Інваріант на ≥10 комбінаціях | ✅ прийнято (+ «з них ≥5 неподільних») | |
| 15 рядків виводу `npm test` | ✅ прийнято | |
| Конкретні входи `(100, 3)`, `(1, 3)`, `(7, 2)`… | ❌ відхилено | це підказка з відповіддю: промпт знаходив би ваду за агента і перестав би бути перевикористовуваним |
| Точні межі «великих сум» (`MAX_SAFE_INTEGER / 1000`) | ❌ відхилено | зайва прив'язка до реалізації |

## 01b / 01c — v2 у двох діалектах

Обидва прогони — паралельно, з одного коміту, з однаковими дозволами.

| | markdown (01b) | XML (01c) |
|---|---|---|
| Ходів / вартість / час | 15 / $0.53 / 149 с | 12 / $0.40 / 121 с |
| Послідовність | Read×3 → Edit → `npm test` ❌ → Edit → `npm test` ✅ → `typecheck` → `git diff --stat` → Grep `.only\|.skip\|console.log` | Read×3 → Edit → `npm test` ✅ → `typecheck` → `git diff --stat` |
| Змінені файли | лише `app/src/quote.test.ts` (+201) | лише `app/src/quote.test.ts` (+173) |
| `npm test` (незалежно) | ✅ 40 passed \| 13 expected fail | ✅ 30 passed \| 9 expected fail |
| `npm run typecheck` | ✅ | ✅ |
| Знайдена вада | `splitInstallments`: `(100,3)` → сума 99, `(2,3)` → 3, `(1000,7)` → 1001 | `splitInstallments`: `(100,3)` → 99, `(10,3)` → 9, `(1,3)` → 0 |
| Відкриті питання | 5: від'ємні входи, знижка поза 0..100, `parts ≤ 0`, дробові входи, від'ємний `totalCents` | 5: те саме + **дробові центи у `formatMoney`** |

Перевірка acceptance criteria:

| Критерій | md | XML |
|---|---|---|
| Крайові випадки: 0, від'ємні, залишок, **половина цента**, великі суми | ⚠️ тест «половина цента» насправді точний (50 % від 100 ¢) | ✅ `1 ¢ × 50 %` → `Math.round(0.5)` |
| Параметризований інваріант ≥10, з них ≥5 неподільних | ⚠️ розірваний: `it.each` лише з подільними + окремий цикл з 10 неподільними | ✅ одна таблиця: 11, з них 6 неподільних |
| `Number.isInteger` | ✅ | ✅ |
| `it.fails` з правильним assertion і коментарем `// ВАДА:` | ✅ | ✅ |
| Наявні тести не змінено | ✅ | ✅ |
| Змінено лише тестовий файл | ✅ | ✅ |
| Без `.only` / `.skip` / `console.log` | ✅ (перевірив сам Grep-ом) | ✅ |
| `npm test` + `typecheck` зелені | ✅ | ✅ |
| Невизначена поведінка не закріплена тестом | ✅ | ✅ |

**Цікавий момент у 01b:** агент помилився в очікуваному значенні
(`expected 899 to be 900`), перерахував `999 − 99.9 = 899.1 → 899` і виправив
**тест**. Тут код був правильний, але саме так виглядає небезпечний патерн
«підігнати тест під реалізацію» — його має ловити рев'ю.

## Порівняння зі слабким промптом

| | 00b: слабкий + «розшир покриття» | 01c: `add-tests` v2 (XML) |
|---|---|---|
| Як знайшов, що читати | субагент шукав `app.py` і pytest, розвідка по репо | 3 файли з «Контексту» |

| Вартість | $0.58 (2 ходи людини) | $0.40 (1 хід) |

## Рішення

- На гілку взято результат **XML-прогону без ручних правок** (`git apply` його
  дифу): він повніше виконав acceptance criteria. Недоліки, які лишились у
  файлі, свідомо не правились руками — їх має знайти промпт рев'ю.
- Відкриті питання щодо контракту лишаються відкритими й документуються
  (рішення людини); вада `splitInstallments` виправляється окремим промптом
  дебагу з рішенням продукту «залишок — у перші платежі».

## Чи відчули різницю між діалектами

Мало. Обидва прогони дали однакову структуру тестів (ті самі `describe`), той
самий формат звіту й ту саму ваду. XML-прогін трохи точніше виконав критерії й
був дешевшим, але це **один прогін на діалект** — відрізнити вплив діалекту від
звичайної варіативності моделі за такою вибіркою не можна. Для цієї моделі
markdown-заголовків достатньо. XML виправданий там, де промпт вбудовують разом
із **чужими даними**: теги дають чітку межу «ось інструкція — ось дані», і це
вже питання безпеки (Task C).
