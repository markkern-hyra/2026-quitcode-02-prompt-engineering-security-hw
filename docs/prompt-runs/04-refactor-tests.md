## Порушення

Промпт: «Не додавай нових перевірок». Агент **додав**: точні очікування
`(10, 3)` → `[4, 3, 3]` і `(1, 3)` → `[1, 0, 0]` (раніше перевірялась лише
сума), а кожен рядок таблиці `splitInstallments` тепер перевіряє ще й довжину,
суму, цілі значення та `max − min ≤ 1`. Тести від цього сильніші, але це саме
те, що рефакторинг робити не мав: зміна того, *що* перевіряється.

Жоден критерій цього не ловить — «кожна пара лишилась» і «файл коротший»
виконуються й при додаванні перевірок. Чесніше формулювання для наступної
версії: «кількість `expect` на кожен вхід не зросла».

## 04b — v2 (після рев'ю CodeRabbit)

Що змінено: критерій «кількість `expect` на пару (функція, вхід) не зросла»;
відновлення після мутацій із копії `.orig` замість `git checkout --` і стоп на

|---|---|

| Відновлення мутацій | перевірка `git status --short app/src/quote.ts` на старті; 12 циклів `cp … quote.ts.orig` → тести → `mv … quote.ts`; наприкінці `.orig` немає, `git diff app/src/quote.ts` порожній ✅ |

| `npm test` / typecheck (незалежно) | ✅ 34 passed / ✅ |
| Таблиця `expect` агента | «Жоден рядок не має „після“ > „до“» |

**Незалежна перевірка таблиці — порушення.** Для входу `(1_000_000_000, 4)` у
базовому файлі (`9ad3fd6`, тест «обробляє великі суми») було **5** перевірок:
`toHaveLength` + 4 × `Number.isInteger`, суми не було. Після рефакторингу тест
«(1_000_000_000, 4): довжина, цілі числа, сума» має **6** — додано суму. У
таблиці агента для цього входу — «6 | 6»: «до» він порахував читанням коду й
помилився. Для `(100, 3)` кількість зменшилась (7 → 6), але одну з
дубльованих сум замінила нова `toHaveLength(3)` — надлишкова поруч із
`toEqual([34, 33, 33])`.

Висновок: **таблиця, яку агент заповнює сам, не є перевіркою** — він
«підтвердив» критерій, який порушив. Промпт → v3: числа лише з механічного
лічильника Vitest (`expect.getState().assertionCalls` в `afterEach`, виведення
через `--reporter=verbose`). Механізм перевірено окремою пробою до прогону:
для тесту `(1_000_000_000, 4)` лічильник показав рівно 5. На гілку результат
не брався — лишається результат v1.

## 04c — v3 (друга ітерація після рев'ю CodeRabbit)

Що змінено: кількість перевірок — лише з механічного лічильника Vitest
(`expect.getState().assertionCalls` в `afterEach`, сирі рядки `ASSERT` до й після
у звіті); назви тестів після рефакторингу містять вхід. Від того самого
`9ad3fd6`, з `Bash(node:*)` у `deny`. Сирий вихід —
[`f2-refactor-tests-v3`](./raw/f2-refactor-tests-v3.md).

| | |
|---|---|
| Ходів / вартість / час | 66 / $2.84 / 441 с; 0 спроб `node`; 1 відмова (комбінована `cp … && sed -i …`) |

| `(1_000_000_000, 4)` | ✅ **5 → 5** — порушення v2 (додана сума) не повторилось |
| `npm test` / typecheck (незалежно) | ✅ 34 passed / ✅ |

**Нова прогалина — зіставлення «тест → вхід» лишилось ручним.** Числа лічильника
правильні, але агент розносив їх по входах, читаючи назви тестів, а старі тести
«повертає масив з parts елементів» і «кожен елемент є цілим числом» входу в
назві не мають:

| Вхід | Агент: до → після | Насправді (з рядків `ASSERT`) | Наслідок |
|---|---|---|---|
| `(100, 3)` | 5 → 5 | **7** → 5 (не врахував «кожен елемент є цілим числом = 3») | критерій виконано, але таблиця неточна |
| `(100, 4)` | 1 → 1 | **2** → 1: було `toHaveLength(4)` і сума = 100 в таблиці інваріанту; лишилась тільки довжина | ❌ **перевірку суми для `(100, 4)` втрачено**, хоча критерій вимагає зберегти кожну пару «вхід → очікування» |

Мутації 6/6 цього не показали: жодна з них не ламає суму саме на подільному
вході. Висновок: механічний лічильник закрив «додані перевірки», але поки
**зіставлення тестів із входами** робить агент, воно може сховати й додавання, й
втрату. Наступний крок (не виконувався): механічне зіставлення — у тимчасовому
інструментуванні логувати кожен виклик функції з назвою поточного тесту
(`CALL <тест> splitInstallments(100, 4)`), щоб і лічильники, і входи бралися з
виводу, а не з читання коду. На гілку результат v3 не брався — лишається v1, де
сума для `(100, 4)` є.
