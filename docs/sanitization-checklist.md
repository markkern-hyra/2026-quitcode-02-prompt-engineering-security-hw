# Чек-ліст санітизації даних для роботи з AI

**Коли застосовувати:** будь-який документ клієнта — бриф, лист, заявка,
вигрузка, лог, скрін — перед тим, як він потрапить у промпт, у робочу папку
агента чи в AI-інструмент.

Приклад застосування: [`sanitized-brief.md`](./sanitized-brief.md).

## 0. Спершу — де лежить оригінал

- [ ] Оригінал **не лежить** у робочій папці агента (репозиторій, відкрита
      папка в Cursor). Агент на запит «розберись у проєкті» читає все підряд.
      > Реальний випадок у цій домашці: на запит «investigate and explain this
      > repo» агент прочитав `materials/client-brief.md` повністю — разом із
      > ключами й контактами. Дані синтетичні, але справжні витікають саме так.
- [ ] Якщо файл мусить бути поруч — його читання заборонено в налаштуваннях
      агента (`permissions.deny` у `.claude/settings.json`, `.cursorignore`).
- [ ] Санітизуємо **локально** (редактор, grep, скрипт), а не вставкою оригіналу
      в чат із проханням «замаскуй».

## 1. Класифікація (світлофор)

| Рівень | Категорія | Приклади | Куди можна | Що робимо |
|---|---|---|---|---|
| 🔴 | Секрети інтеграцій | API-ключі, bot-токени, PAT, паролі, connection strings, URL вебхуків, n8n credentials | нікуди | out-of-band |
| 🔴 | PII | ПІБ, email, телефон, адреса, особисті месенджери, номери документів | нікуди в публічну модель | плейсхолдер / маска / прибрати |
| 🔴 | Продакшн-дані | вигрузки таблиць, логи з даними користувачів, скріни CRM | нікуди | синтетика того самого формату |
| 🟡 | Внутрішня комерція | ставка, собівартість, маржа, умови угоди, конкуренти, дедлайни пропозицій | лише tier із розділу 5 | прибрати або `<INTERNAL>` |
| 🟡 | Ідентичність клієнта й внутрішня логіка | назва компанії, внутрішні хости, назви баз і таблиць, схеми | лише tier із розділу 5 | `[CLIENT_1]`, узагальнити |
| 🟢 | Постановка задачі | проблема, процес, критерії приймання, обсяги без даних, галузь | будь-яка модель | лишити дослівно |

Сумнівні випадки:
- **URL вебхука** — 🔴, а не 🟡: хто знає адресу, той може слати в неї запити.
- **Назва клієнта** — 🟡 сама по собі, але поруч із комерцією чи конкурентами
  стає чутливішою — маскуємо.
- **Роль контакту** («керівник операцій») — 🟢, якщо без імені: вона пояснює,
  хто приймає роботу.

## 2. Як маскуємо

| Техніка | Коли | Приклад |
|---|---|---|
| Redaction | поле не потрібне для задачі | особистий месенджер → `<REMOVED>` |
| Masking | важливий формат, не значення | `+380 (XX) XXX-XX-XX`, `****-1234` |
| Плейсхолдер | сутність потрібна, особа — ні | `[CLIENT_1]`, `[CONTACT_1]`, `[CONTACT_1_EMAIL]` |
| Synthetic | потрібні приклади даних | рядки того самого формату, явно вигадані: код оператора `(00)`, `м. Тестове` |
| Out-of-band | будь-який секрет | `<SECRET_OUT_OF_BAND>` + назва змінної (`CRM_API_KEY`) |
| Узагальнення | комерція | `<INTERNAL>` |

Правила:
- **Задача має лишатись зрозумілою.** Після маскування перечитай «що зробити» й
  «критерії приймання» без оригіналу. Не зрозуміло — замаскували зайве.
- **Плейсхолдери консистентні:** `[CONTACT_1]` — та сама особа по всьому
  документу. Таблиця відповідностей лежить локально — не в документі й не в
  промпті.
- **Синтетика корисна для задачі:** додай рядки з крайовими випадками, які
  задача має обробити (некоректний телефон, порожня адреса).
- **Синтетика не схожа на реальних людей:** не «справжнє прізвище з вигрузки +
  цифра», а явно вигадане — `[CUSTOMER_1]`, `м. Тестове`. І не бери прикладів
  з оригіналу навіть у чек-ліст чи навчальні матеріали.

## 3. Креденшели інтеграцій

- [ ] Секрет не потрапляє ні в документ, ні в промпт, чат, коміт, скрін чи тікет.
- [ ] У документі — сервіс, навіщо він у задачі, назва змінної або n8n
      credential; значення — `<SECRET_OUT_OF_BAND>`.
- [ ] Роль сервісу — **лише з того, що сказав клієнт.** Не назвав — пиши «у
      брифі не вказано»; наш висновок (напр. з назви вебхука) — з позначкою
      `ПРИПУЩЕННЯ`. Інакше модель прийме наше припущення за факт: у цій
      домашці непозначена «роль» Airtable двічі зробила специфікацію хибною,
      а після позначки «не вказано» той самий промпт поставив питання.
- [ ] Агент отримує секрет лише через env на етапі запуску; `.env` — у
      `.gitignore`, читати `.env` агенту заборонено.
- [ ] В n8n — посилання на credential за назвою, а не значення в Code чи HTTP
      node.
- [ ] Для розробки з AI — окремі dev/test-ключі з мінімальними правами, не прод.
- [ ] Секрет потрапив у модель, чат або git → він **скомпрометований**: ротація
      одразу. Видалення з історії чи чату витоку не скасовує.

## 4. Перевірка перед відправкою

**Крок 1 — автоматично (формати).** Ловить ключі й токени, connection strings,
вебхуки, email, українські телефони (`+380…` і локальні `0XX…`), @-хендли.
Порожній вивід — формати чисті:

```bash
grep -nEi '(api[_-]?key|token|secret|passw|bearer|\bpat[A-Za-z0-9]*\.|xox[abprs]-|\bsk-|\bfake_|://[^ /:]+:[^ @]+@|(postgres(ql)?|mysql|mongodb(\+srv)?|redis|amqp)://|/webhook/|[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}|\+?380[ ()-]*[0-9]{2}[ )-]*[0-9]{3}|\b0[0-9]{2}[ )-]*[0-9]{3}[ -]?[0-9]{2}[ -]?[0-9]{2}\b|(^|[ (])@[A-Za-z0-9_]{5,}|t\.me/|\bapp[A-Za-z0-9]{10,})' ФАЙЛ.md \
  | grep -vE '<SECRET_OUT_OF_BAND>|\(XX\)|\(00\)'
```

Те саме одним викликом, без показу вмісту (лише категорія, номери рядків і
кількість) — зручно давати й агентові, як у команді `/sanitize-check`:

```bash
bash docs/tools/sensitive-lines.sh ФАЙЛ.md
```

Очікувані хибні збіги — **назви** змінних (`CRM_API_KEY`, `SLACK_BOT_TOKEN`) і
звичайні слова («secret» у тексті): це нормально, якщо в рядку немає значення.
Так спрацював grep на специфікаціях, які агент згенерував із санітизованого
брифу: по 3 збіги — назви змінних і слово «secret» у питанні про автентифікацію
вебхука, жодного значення.

Обмеження: `grep -v` в allowlist відкидає рядок **цілком** — якщо поруч із
плейсхолдером опиниться справжнє значення, grep його не покаже. Рядки з
плейсхолдерами переглядай очима.

**Крок 2 — вручну (те, чого regex не бачить).** Імена, назви компаній, адреси й
комерцію шаблоном не зловиш: на оригінальному брифі grep знайшов 11 рядків, але
пропустив ПІБ контакту, назву клієнта й усю комерційну частину.

- [ ] Прочитав документ повністю й кожному блоку поставив 🔴/🟡/🟢.
- [ ] Немає жодного справжнього ПІБ, назви клієнта, адреси.
- [ ] Немає ставок, собівартості, маржі, згадок про конкурентів.
- [ ] Вигрузки замінені синтетикою.
- [ ] Секрети — лише `<SECRET_OUT_OF_BAND>` + назва змінної.
- [ ] Задача й критерії приймання зрозумілі без оригіналу.
- [ ] Обраний інструмент відповідає **найвищій** категорії, що лишилась у
      документі (розділ 5).

## 5. Інструмент під категорію

| Найвища категорія в документі | Інструмент / режим | Чому |
|---|---|---|
| 🟢 | будь-який: Claude Team, особисті Pro/Max, Claude Code, Cursor | даних клієнта немає |
| 🟡 (людина в чаті) | **лише Claude Team** — робочий простір компанії | комерційні умови: дані не йдуть у навчання моделей за замовчуванням; акаунтами керує компанія |
| 🟡 (автоматизація, n8n → LLM) | API з комерційними умовами; ключ — у n8n credentials | ті самі умови без людини в чаті; ключ не в документі й не в промпті |
| 🔴 секрети | жоден AI-інструмент | лише out-of-band через env |
| 🔴 PII, продакшн-дані | жоден — спершу санітизувати до 🟢/🟡 | tier не скасовує обов'язків щодо персональних даних клієнтів; виняток — лише письмова політика компанії чи договір із клієнтом |

### Чому для 🟡 саме Claude Team

Команда QuitCode вже працює в Claude Team, тож 🟡-документи — маржа, назва
клієнта, внутрішня логіка систем — обробляємо лише там. Вирішальне тут — умови
використання, а не якість моделі: Team — комерційний продукт, де дані за
замовчуванням не використовуються для навчання моделей, а акаунтами керує
компанія (додати чи прибрати людину, спільні правила). Особисті Pro/Max —
споживчі плани: чи підуть чати в навчання, залежить від налаштування
приватності конкретної людини, і компанія не може цього ні гарантувати, ні
перевірити. Тому «у мене вимкнено навчання» — не аргумент для 🟡: правило має
триматися на обраному інструменті, а не на налаштуваннях окремого акаунта.
Цю домашку я виконував на особистому плані — прийнятно лише тому, що всі дані
синтетичні; зі справжнім брифом це порушило б цей самий чек-ліст. Локальна
модель (напр. Ollama) — опція на майбутнє для першого проходу санітизації, поки
документ ще містить 🔴. Умови провайдерів змінюються: перевіряти їх щонайменше
раз на квартал (стан — вересень 2026).

## 6. Якщо щось витекло

- **Секрет:** ротація одразу, перевірити журнал використання ключа.
- **PII:** повідомити відповідального в компанії; зафіксувати що, куди й коли.
- **Не** просити модель «забути» — це нічого не видаляє.
