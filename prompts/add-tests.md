# Тести для модуля з грошовою логікою

## Роль

Senior TypeScript-розробник, який пише тести для фінансової логіки й шукає
дефекти, а не підтверджує поточну поведінку.

## Мета

Розширити покриття `app/src/quote.ts` тестами на крайові випадки й грошові
інваріанти так, щоб вони виявили реальні вади, — не змінюючи продакшн-код.

## Контекст

- Прочитай перед роботою: `app/src/quote.ts` (три експортовані функції),
  `app/src/quote.test.ts` (наявні happy-path тести), `app/package.json`
  (Vitest, `"type": "module"`).
- Домен: кошторис проєкту; усі суми — цілі числа в центах (див. докстрінг
  модуля). Округлення не повинно створювати чи губити центи.
- Імпорт у тестах — `./quote.js` (NodeNext), як у наявному файлі.
- Команди: `cd app && npm test`, `cd app && npm run typecheck`.

## Обмеження

- Змінюй лише `app/src/quote.test.ts`. `app/src/quote.ts` не чіпай, навіть
  якщо знайшов ваду, — виправлення це окрема задача.
- Наявні тести не видаляй і не переписуй — лише додавай нові.
- Не додавай залежностей (без fast-check тощо): наборові перевірки — звичайними
  циклами або `it.each` по фіксованих значеннях.
- Тести детерміновані: без `Math.random` і без залежності від часу.
- Не вигадуй контракт: якщо поведінку для входу не визначено ні кодом, ні
  докстрінгом, не закріплюй поточну поведінку як правильну — винеси це у
  «Відкриті питання».
- Назви тестів — українською, у стилі наявних (`describe` + `it`).

## Acceptance criteria

- [ ] Для кожної з трьох функцій розглянуто крайові випадки — 0, від'ємні
      значення, неподільний залишок, округлення половини цента, великі суми:
      кожен або покрито тестом, або (якщо контракт його не визначає) внесено
      у «Відкриті питання».
- [ ] Для функцій, що ділять або перераховують гроші, є параметризований
      тест-інваріант «центи не з'являються і не зникають» (сума частин
      дорівнює цілому) на наборі щонайменше з 10 комбінацій, з них ≥5
      неподільних.
- [ ] Для функцій, що повертають центи, є перевірка `Number.isInteger` на
      цілих входах.
- [ ] Кожен тест, що падає на поточному коді, оформлено як `it.fails(...)`:
      assertion перевіряє **правильну** поведінку, а над тестом стоїть коментар
      `// ВАДА: <функція>(<вхід>) → <факт>, очікується <очікування>`.
- [ ] Наявні тести не видалено й не змінено.
- [ ] `git diff --stat` показує зміни лише в `app/src/quote.test.ts`.
- [ ] У файлі немає `.only`, `.skip`, `console.log`, `debugger`.
- [ ] `cd app && npm test` зелений (включно з `it.fails`), `cd app && npm run
      typecheck` без помилок.
- [ ] Жоден тест не закріплює поведінку, яку код і докстрінги не визначають
      (напр. `parts ≤ 0`, знижка поза 0..100, від'ємні `hours` / `rateCents`);
      кожен такий випадок — окремим пунктом у «Відкритих питаннях».

## Формат відповіді

1. Таблиця `функція | що перевіряє тест | результат (✅ проходить / 🐞 it.fails)`.
2. Знайдені вади: для кожної — функція, мінімальний вхід, фактичний і
   очікуваний результат.
3. Відкриті питання щодо контракту — що має вирішити людина.
4. Останні 15 рядків виводу `npm test`.

## Stop

Після зеленого `npm test` зупинись: не виправляй `quote.ts`, не рефактори й не
додавай інших тестових файлів. Покажи звіт і чекай на рішення щодо знайдених вад.

Для порівняння: слабкий промпт з уточненням лишив **червоний** `npm test`
(3 failed) і оголосив роботу завершеною — [00-weak-prompt.md](../docs/prompt-runs/00-weak-prompt.md).

**Чи відчули різницю між діалектами?** Мало: однакова структура тестів і звіту,
та сама вада. XML-прогін трохи точніше виконав критерії (справжній тест на
половину цента, одна таблиця інваріанту), але це один прогін на діалект — від
варіативності моделі не відрізнити. XML корисніший там, де промпт містить чужі
дані: теги відділяють інструкції від даних.

## Журнал змін

- **v2, правки без зміни змісту (після незалежного рев'ю)** — правопис
  («не рефактори»); XML-діалект синхронізовано з markdown: повернуто пропущені
  при перекладі «без fast-check», «для функцій, що ділять або перераховують
  гроші» і «напр.». Прогони 01b/01c виконувались на тексті до цих правок.
- **v2** — після meta-prompting (агента попросили покращити v1 перед
  виконанням). Прийнято: заборона змінювати наявні тести; заборона
  `.only`/`.skip`/`console.log`; інваріант `Number.isInteger`; вимога, щоб
  `it.fails` перевіряв правильну поведінку; перелік невизначених випадків;
  набір інваріанту ≥10 комбінацій; 15 рядків виводу тестів. Відхилено:
  конкретні входи на кшталт `(100, 3)` — вони підказують ваду й прив'язують
  промпт до одного файлу, тож він перестає бути перевикористовуваним.
- **v1** — перша версія за `_template.md`.
